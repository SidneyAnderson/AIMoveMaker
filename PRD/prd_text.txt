Section 1: Executive Summary
1.1 Product Vision
AI Movie Maker is a standalone, web-based, end-to-end AI film production platform. Users produce complete short-form video content — from initial concept through final rendered output — using AI-generated images, video, and audio, without requiring expertise in the underlying model architectures, inference parameters, or video production pipelines.
The platform abstracts the complexity of diffusion models, video generation models, ControlNet pipelines, LoRA composition, and audio synthesis behind a modern, professional-grade user interface modelled on non-linear video editing conventions. The backend handles all model routing, hardware profiling, queue management, and pipeline orchestration autonomously.
1.2 Core Value Proposition
A Creative user produces a complete storyboard of AI-generated images using any registered model and LoRA combination, with full keyframe control, seed management, and image editing — without writing code or configuring pipeline parameters.
An Engineer user takes that storyboard and produces a finished video with AI-generated motion, ControlNet-guided consistency, frame interpolation, and a full AI-generated audio track.
The system runs entirely on local hardware (RTX 5090, 32GB VRAM) with transparent, user-confirmed burst capability to Vast.ai datacenter GPUs for high-demand workloads.
The pipeline is model-agnostic. Adding a new image, video, or audio model requires only registering it in the Model Registry — no frontend or pipeline code changes required.

2.4 User Lifecycle
This section defines how user accounts are created, authenticated, approved, and deactivated. Two creation paths exist: direct Admin creation and invite-based self-registration.
2.4.1 First-Boot Bootstrap
On first server startup, setup.sh seeds a single Admin account: email 'admin@localhost', password 'admin'.
This account has global_role='admin' and is_active=true. It bypasses pending approval.
The system MUST detect first login by this bootstrap account and force an immediate password change before granting access to any other screen. Tracked via force_password_change bool on User (default false; set true on bootstrap seed).
Until the password is changed, all API requests from this account other than POST /auth/change-password MUST return HTTP 403 with error code 'password_change_required'.
WARNING: The default admin credential is for local bootstrap only. The system MUST display a prominent warning banner in the Admin UI until the default password has been changed.
2.4.2 Direct Admin Creation
Admin creates a user via the Admin panel (POST /users). Required fields: full_name, email, password.
Directly created accounts are immediately active: is_active=true, approval_state='approved'. No approval gate.
The created user receives an in-app and email notification that their account is ready.
force_password_change is set to true. The user MUST change their password on first login before accessing any other screen.
2.4.3 Invite-Based Registration
Admin sends an invite link to a prospective user. The link leads to an account creation page. The invited user creates their own account and waits for Admin approval before gaining system access.

2.4.4 OAuth Authentication — Google and Discord
OAuth 2.0 social login is available on the invite registration page and the standard login page. Supported providers: Google and Discord. Both are completely free to implement.

OAuth flow is backend-driven authorization code flow with PKCE. Frontend initiates by redirecting to GET /auth/oauth/{provider}/authorize. Backend handles callback at GET /auth/oauth/{provider}/callback.
New email (no existing account): a new User record is created with email + full_name from provider, password_hash=null, and an OAuthIdentity record linking provider + provider_user_id to the account. If triggered from an invite link, the invite token is passed through the OAuth state parameter and validated on callback.
Existing email (account already exists): OAuth identity is merged. A new OAuthIdentity record is created linking provider + provider_user_id to the existing user. The user is logged in to their existing account. password_hash is preserved.
OAuth provider credentials (client_id, client_secret) stored in Setting table with is_secret=true. Keys: google_oauth_client_id, google_oauth_client_secret, discord_oauth_client_id, discord_oauth_client_secret.
If OAuth credentials are not configured, the corresponding button is hidden from login and registration pages. No error shown.
2.4.5 Login Flow
Standard login: POST /auth/login with email + password. Returns access token (15 min) and refresh token (7 days, rotation on use).
OAuth login: GET /auth/oauth/{provider}/authorize → provider redirect → GET /auth/oauth/{provider}/callback → same token pair returned.
Login by approval_state='pending' user: HTTP 403, error code 'account_pending_approval'.
Login by is_active=false user: HTTP 403, error code 'account_deactivated'.
Login where force_password_change=true: HTTP 403, error code 'password_change_required'. All endpoints except POST /auth/change-password blocked.
Rate limiting: 5 failed attempts per email per 15-minute window triggers a 15-minute lockout. Tracked in Redis.
2.4.6 Password Requirements
Minimum 10 characters.
Must contain at least one uppercase letter, one lowercase letter, one digit, and one special character.
Validated on client (immediate feedback) and server (authoritative). Client validation is UI convenience only.
Hashing: bcrypt, cost factor 12.
Forgotten password: POST /auth/forgot-password with email. Time-limited reset link emailed (1 hour expiry) if address matches an active account. Response always returns HTTP 200 regardless of whether the email exists (prevents email enumeration).
2.4.7 User Deactivation
Admin MAY deactivate any non-Admin user via PATCH /users/{id} setting is_active=false.
On deactivation: all active sessions invalidated immediately (refresh tokens revoked in Redis). All queued jobs owned by user are cancelled. Project memberships retained.
Deactivated users shown in Admin list with 'Deactivated' badge. Hidden from all project member selectors.
Admin accounts MUST NOT be deactivatable via the UI. Admin must first demote the account to global_role='user' before deactivation is permitted.
Acceptance Criteria: GIVEN an invited user who has completed registration WHEN they attempt to log in before Admin approval THEN they receive HTTP 403 with error code 'account_pending_approval'. GIVEN Admin approves the user THEN the user receives an email notification AND can log in AND is visible in the project member selector.

3.4 Deployment — No Docker
The system deploys as a Python virtual environment on a Linux host. Docker is NOT used for standard deployment.
setup.sh: Creates Python venv, installs pinned requirements.txt, creates directory structure, runs Alembic migrations, seeds default Admin user and required system settings.
start.sh: Activates venv, starts Redis if not running, starts Celery worker, starts FastAPI server via uvicorn. All processes log to /opt/aimoviemaker/logs/ with daily rotation.
requirements.txt: All dependencies at exact pinned versions.
Exception: The Vast.ai remote job runner MAY use an isolated environment on the datacenter instance. This is the only permitted use of container-based isolation and applies only to the remote side.

Section 4: Feature Specifications — Creative Domain
All features in this section are accessible to the Creative persona (and Admin in Creative role). Active only when the project is in CreativeActive state.
4.1 Storyboard Mode
The Storyboard is the primary Creative workspace. It presents all Keyframes as a scrollable, reorderable grid of image cards. It is the Creative's exclusive view before handoff to Engineering.
4.1.1 Storyboard Grid
Keyframe cards display: thumbnail of selected_asset, keyframe index, prompt excerpt (first 80 chars), model name, seed value.
Cards are drag-and-drop reorderable. Reordering updates the index field on all affected Keyframes atomically.
Card actions: Regenerate, Edit in Canvas, Duplicate, Delete, Set Selected Asset (from candidate carousel).
Grid zoom levels: 1-up (large), 3-up, 6-up (default), 12-up (overview).
Generate All button queues image generation jobs for all Keyframes that have no selected_asset.
4.1.2 Keyframe Creation
New Keyframe appends a blank keyframe at the end of the storyboard.
Insert Before / Insert After via context menu inserts at a specific position.
Duplicate copies the source keyframe's full prompt, model, LoRA stack, params, and seed into a new keyframe.
A Keyframe MUST have at least a positive_prompt before a generation job can be queued.
4.1.3 Handoff Submission
Submit to Engineering button is available only in CreativeActive state.
Before submitting, the system validates all keyframes have a selected_asset. If any do not, a non-modal warning lists the incomplete keyframes. The Creative MAY proceed anyway or cancel.
On submission, project transitions to PendingHandoff. A Notification is sent to the assigned Engineer via all configured channels within 30 seconds.
Acceptance Criteria: GIVEN a project in CreativeActive with all keyframes having selected assets WHEN Creative clicks Submit to Engineering THEN project state becomes PendingHandoff AND Engineer receives a notification within 30 seconds.

4.2.3 Candidate Asset Management
When variation_count > 1, the generation job produces multiple Asset records all linked to the same Keyframe via candidate_asset_ids.
The Storyboard card shows a carousel of candidate thumbnails. Creative clicks one to set it as selected_asset_id.
Candidate assets not selected are retained in storage indefinitely. They are never auto-deleted.
The Creative MAY regenerate at any time, producing new candidates without destroying existing ones.
Acceptance Criteria: GIVEN a Keyframe with seed_mode=variation and variation_count=4 WHEN generation completes THEN 4 Asset records exist AND all 4 thumbnails appear in the candidate carousel AND selecting one updates selected_asset_id.

Section 6: Feature Specifications — Infrastructure and Admin
6.1 Model Registry
The shared library of AI models. Managed by Admin and Engineer. All Keyframe, VideoClip, and AudioClip model references point to ModelRegistry records.
6.1.1 Model Registration Paths
Download from HuggingFace by repo ID (uses huggingface_hub snapshot_download).
Download from Civitai by model ID (fetches download URL from Civitai API, downloads server-side).
Point to existing local path on the server filesystem.
On registration, the system computes sha256_hash of the model file for integrity and deduplication. If a model with the same sha256_hash already exists, registration is rejected with a clear error identifying the existing record.
Admin or Engineer MUST provide: name, display_name, type, architecture, vram_floor_mb, param_schema.
System SHOULD auto-detect architecture and vram_floor_mb from model file metadata (e.g. Diffusers model_index.json) where possible.
6.1.2 param_schema Format
A JSONB field defining the UI controls rendered for this model. Each key is a parameter name. Each value is a control definition.
{ "steps":     { "type": "int",   "min": 1,   "max": 150, "default": 30,    "label": "Steps" },
  "cfg_scale": { "type": "float", "min": 1.0, "max": 20.0,"default": 7.0,   "label": "CFG Scale" },
  "sampler":   { "type": "enum",  "values": ["euler","dpm++","ddim"], "default": "euler", "label": "Sampler" } }
Supported control types: int (slider), float (slider), enum (dropdown), bool (toggle), string (text input).
The frontend MUST render controls from param_schema without any model-specific hardcoded logic.
6.1.3 VRAM Profiler
Before any generation job is queued, the VRAM Profiler calculates estimated VRAM based on: model vram_floor_mb, resolution (width x height), frame count (video only), LoRA stack size, and active precision (fp16/bf16/fp8).
If estimated VRAM exceeds available local VRAM minus 10% safety margin, the system MUST show a non-blocking modal: estimated VRAM required, available local VRAM, top 3 Vast.ai instance options with specs and cost estimate, and a Confirm and Send to Cloud button.
The user MUST click Confirm before the job is dispatched to Vast.ai. This gate MUST NOT be bypassable by any setting or system override.
If user declines, the job is not queued and the user returns to the generation panel.
6.2 LoRA Registry
Registration: download from Civitai, download from HuggingFace, or point to local path.
Fields: name, display_name, architecture, storage_path, source_url, hf_repo_id, civitai_id, trigger_words (json array), nsfw_flag (bool), weight_default (float), file_size_bytes, sha256_hash.
NSFW LoRAs are stored and displayed without filtering. No content restriction is applied by the application.
LoRA browser silently filters to show only LoRAs whose architecture matches the currently selected model. No error is shown for filtered LoRAs — they simply do not appear.

6.3.2 Queue Behavior
Single shared Celery queue. Priority order: HIGH > MEDIUM > NORMAL > LOW.
Admin MAY cancel any job in any state. Creative and Engineer MAY cancel their own jobs if status is 'queued' or 'running'.
Failed jobs retry automatically up to max_retries (default 2). After max_retries, status='failed'. Non-modal warning appears in the Log Viewer panel.
Critical failures (OOM, corrupt model file) display as a modal error with error_code and a link to the full log entry.
Batch jobs share a batch_id. Batch entity tracks job_count, done_count, failed_count for progress display.
6.3.3 Progress Streaming
Every running Job streams progress via Redis pub/sub to the FastAPI WebSocket endpoint /ws/jobs/{job_id}.
Progress updates MUST include: progress_pct (0-100), current_step, total_steps, eta_seconds, status.
Update interval: every 500ms during active generation.
Progress meters displayed pervasively: job panel, keyframe card (during image gen), timeline clip (during video gen), global status bar.
WebSocket connection MUST auto-reconnect on disconnect with exponential backoff (max 30 second interval).
6.4 Vast.ai Integration
6.4.1 Routing Flow
VRAM Profiler flags job as exceeding local capacity.
System fetches current Vast.ai offers via vastai SDK, filtered by minimum VRAM, CUDA version, and cost per hour.
Confirmation modal displays: top 3 instance options with GPU specs, VRAM, and estimated cost for the job.
User selects an instance and clicks Confirm and Send to Cloud.
System provisions the selected instance.
System transfers required model files and job payload to the instance. Transfer size and duration MUST be logged.
Job executes on Vast.ai instance. Progress streams back to local WebSocket.
On completion, output files transfer back to local outputs/ directory.
Vast.ai instance is terminated. Actual cost recorded in job.cost_actual_usd.
WARNING: Cost Estimate Disclaimer: The cost estimate shown before routing is based on instance hourly rate multiplied by estimated job duration. Actual cost may vary. This MUST be stated explicitly in the confirmation modal.
Vast.ai API key stored in Setting table (key='vastai_api_key', is_secret=true).
If Vast.ai instance fails mid-job: job status = 'failed', instance is destroyed, user is notified. No automatic retry on Vast.ai.

Section 8: Non-Functional Requirements
8.1 Logging
All log output is structured JSON. Every line MUST include: timestamp (ISO 8601 UTC), level (DEBUG/INFO/WARNING/ERROR/CRITICAL), logger name, message, trace_id.
trace_id is a UUID generated per HTTP request and propagated through all downstream calls and Celery tasks via Python context variable.
Log files written to /opt/aimoviemaker/logs/ with daily rotation. Retention: 30 days.
Frontend Log Viewer displays backend logs in real time via /ws/logs WebSocket, filterable by level, trace_id, job_id, project_id, and time range.
All AI inference calls MUST log: model_id, input parameters (prompt text at TRACE level only), VRAM before/after, duration_ms, output asset path.
All Vast.ai operations MUST log: instance_id, specs, estimated_cost, actual_cost, transfer_size_mb, duration_ms.
Secret Setting values MUST NOT appear in any log. Log '[REDACTED]' for all fields where is_secret=true.

11.1 Design Language
Aesthetic
Dark professional tool with color accents. Primary reference: DaVinci Resolve / Adobe Premiere. Deep panel chrome, structured toolbar regions, application-weight shell — this is a dedicated production tool, not a SaaS dashboard. Secondary reference for component styling only: VS Code / Cursor.

Minimal and purposeful. Use Framer Motion for: panel transitions, modal entrance/exit, progress bar fills, drag-and-drop feedback. No decorative animations. Duration cap: 200ms for micro-interactions, 300ms for panel transitions.

12.3 API Contract — Pydantic-First
The API contract is defined through Pydantic models in backend/schemas/. FastAPI consumes these models and auto-generates the OpenAPI spec at /docs and /openapi.json. The Pydantic models are the authoritative contract — not prose, not comments, not separate documentation.
12.3.1 Schema Conventions
Every endpoint group has a corresponding schema file in backend/schemas/. Example: backend/schemas/keyframe.py contains KeyframeCreate, KeyframeUpdate, KeyframeResponse.
All response schemas MUST inherit from a base class that includes id (uuid) and created_at (datetime).
All list endpoints return a paginated envelope: { items: List[T], total: int, page: int, page_size: int }.
All error responses return: { error_code: str, message: str, detail: Any | None }. The error_code field MUST match the codes defined in this PRD (e.g. 'account_pending_approval', 'password_change_required').
UUIDs are serialized as strings in JSON responses.
Datetimes are serialized as ISO 8601 strings with UTC timezone offset.
JSONB fields (lora_stack, params, param_schema, candidate_asset_ids) are serialized as their native JSON structure — not as escaped strings.
12.3.2 WebSocket Message Envelope
All WebSocket messages use a consistent envelope. The agent MUST use exactly this structure for all three WebSocket endpoints.
// Job progress  (/ws/jobs/{job_id})
{ type:progress, job_id:uuid, progress_pct:0-100, current_step:int, total_steps:int, eta_seconds:int, status:running }
// Job terminal states
{ type:done, job_id:uuid, output_asset_id:uuid }
{ type:failed, job_id:uuid, error_code:str, error_msg:str }
// Project events  (/ws/projects/{project_id})
{ type:state_change, project_id:uuid, new_state:str, actor_id:uuid }
{ type:asset_created, project_id:uuid, asset_id:uuid, entity_type:str, entity_id:uuid }
{ type:handoff_event, project_id:uuid, event:submitted|accepted|declined }
// Log stream  (/ws/logs)
{ type:log, timestamp:ISO8601, level:str, message:str, trace_id:uuid, job_id:uuid|null, project_id:uuid|null }
12.3.3 Frontend API Client
The frontend API client lives in frontend/src/api/. It is a typed wrapper around axios.
One file per resource group matching the backend router structure: auth.ts, projects.ts, keyframes.ts, jobs.ts, etc.
Every API function is async and returns a typed response matching the Pydantic response schema. No untyped any returns.
The axios instance is configured with: base URL from VITE_API_URL env var, automatic JWT token injection via request interceptor, automatic token refresh via response interceptor on 401.
During Phase 4 frontend development, the axios instance is intercepted by MSW (Mock Service Worker) which returns mock responses matching the Pydantic schemas. MSW handlers live in frontend/src/mocks/. They are removed and the real axios instance is used in Phase 5.
12.4 Frontend State Management
State management: Zustand. One store per domain: useProjectStore, useStoryboardStore, useTimelineStore, useJobStore, useAuthStore.
Server state (data fetched from API): TanStack Query (React Query). All API fetches go through useQuery / useMutation hooks. Do not store server data in Zustand — Zustand is for UI state only (selected keyframe id, active panel, command palette open state, etc.).
WebSocket state is managed in a custom hook useWebSocket that wraps the native WebSocket, handles reconnection, and dispatches incoming messages to the appropriate Zustand store or React Query cache invalidation.

13.11 Common Response Conventions
Paginated List Response
All GET list endpoints that may return large result sets use this envelope:
{ "items": [ ...ResourceResponse ],
  "total": "int",
  "page": "int",
  "page_size": "int",
  "pages": "int"
}
Error Response Envelope
All error responses (4xx, 5xx) use this envelope:
{ "error_code": "string",            // machine-readable, snake_case
  "message": "string",              // human-readable explanation
  "detail": "object?"               // additional context (e.g. field errors, VRAM stats)
}
Thumbnail URL Convention
All thumbnail_url fields point to GET /projects/{project_id}/assets/{asset_id}/thumbnail.
Thumbnails are JPEG, max 512x512, generated on first request and cached.
If no asset exists yet, thumbnail_url is null — the frontend renders the empty card state.
storage_path Security Rule
The storage_path field on Asset, ModelRegistry, LoRARegistry, and Snapshot entities is NEVER included in any API response. It is a server-side field only. The agent MUST verify no Pydantic response schema includes storage_path.
